# 공통 보안 이벤트 스키마

## 1. 개요

본 문서는 Defense AI 시스템에서 사용하는 공통 보안 이벤트 데이터 구조를 정의한다.

Rocky Linux 에이전트가 수집한 보안 이벤트를 Windows AI 컨트롤러에 전달할 때 동일한 데이터 형식을 사용하기 위한 목적이다.

- 스키마 버전: `1.0`
- 데이터 형식: JSON
- 문자 인코딩: UTF-8
- 시간 기준: UTC
- 초기 구현 언어: Python 3.12

## 2. 시스템 구성

**Rocky Linux Agent**
- 시스템 로그 및 보안 이벤트 수집
- 수집한 데이터를 공통 이벤트 형식으로 변환
- Windows 컨트롤러로 이벤트 전달

**Windows AI Controller**
- 수신 이벤트의 유효성 검사
- 이벤트 분석 및 위협 탐지
- 탐지 결과에 따른 대응 판단

본 스키마는 보안 이벤트의 표현만 담당하며, 네트워크 통신과 실제 대응 명령은 별도로 정의한다.

## 3. 이벤트 필드 정의

| 필드 | 자료형 | 필수 | 설명 |
|---|---|---|---|
| `schema_version` | string | O | 이벤트 스키마 버전 |
| `event_id` | string | O | 이벤트 고유 UUID |
| `occurred_at` | string/null | O | 원본 이벤트 발생 시각 |
| `observed_at` | string | O | 에이전트 관측 시각 |
| `agent_id` | string | O | 수집 에이전트 식별자 |
| `host_id` | string | O | 이벤트 발생 시스템 식별자 |
| `event_type` | string | O | 이벤트 유형 |
| `attributes` | object | O | 이벤트별 추가 정보 |

모든 최상위 필드는 필수이며, `occurred_at`만 `null`을 허용한다.

## 4. 필드별 규칙

### 4.1 schema_version
- 초기 값은 `"1.0"`으로 고정한다.
- 지원하지 않는 버전의 이벤트는 거부한다.

### 4.2 event_id
- UUID 형식의 문자열을 사용한다.
- 초기 구현에서는 UUIDv4를 생성한다.
- 각각의 이벤트는 고유한 ID를 가져야 한다.

### 4.3 occurred_at
- 원본 로그에 기록된 이벤트 발생 시각이다.
- UTC 기반 ISO 8601 형식을 사용한다.
- 발생 시각을 확인할 수 없다면 `null`로 기록한다.

### 4.4 observed_at
- 에이전트가 이벤트를 관측한 시각이다.
- UTC 기반 ISO 8601 형식을 사용한다.
- 필수 값이며 `null`을 허용하지 않는다.

시간 문자열은 `2026-10-13T06:34:00Z` 형태를 사용한다. 두 시간의 순서는 시스템 시계 오차 등으로 달라질 수 있다.

### 4.5 agent_id / host_id
- 공백이 아닌 문자열을 사용한다.
- 에이전트 식별자와 이벤트 발생 시스템 식별자를 구분한다.
- 인증정보나 비밀키를 식별자로 사용하지 않는다.

### 4.6 event_type
- 소문자와 점을 이용한 계층형 이름을 사용한다.
- 초기 지원 유형은 `auth.login_failed`로 한다.
- 새로운 유형은 명세와 검증 규칙을 정의한 후 추가한다.

### 4.7 attributes
- JSON 객체를 사용한다.
- 이벤트 유형에 따라 허용되는 필드가 달라진다.
- 비밀번호, 인증 토큰, 개인키 등 비밀정보는 저장하지 않는다.

## 5. 초기 이벤트 유형

### auth.login_failed

인증 실패 이벤트를 나타낸다.

| 속성 | 자료형 | 필수 | 설명 |
|---|---|---|---|
| `service` | string | O | 인증 서비스 이름 |
| `username` | string | X | 로그인 시도 계정 |
| `source_ip` | string | X | 접속 출발지 IPv4 또는 IPv6 주소 |

`service`는 비어 있지 않아야 한다. 선택 속성은 값이 확인되는 경우에만 포함한다.

## 6. JSON 이벤트 예시

다음은 가상의 SSH 로그인 실패 이벤트다.

```json
{
  "schema_version": "1.0",
  "event_id": "5dc0c97c-9a6b-4f99-ae49-6e4ccacb02aa",
  "occurred_at": "2026-10-13T06:33:59Z",
  "observed_at": "2026-10-13T06:34:00Z",
  "agent_id": "rocky-agent-01",
  "host_id": "rocky-vm-01",
  "event_type": "auth.login_failed",
  "attributes": {
    "service": "sshd",
    "username": "example",
    "source_ip": "192.0.2.10"
  }
}
```

예시 IP 주소는 문서용 주소이며 실제 접속 기록이 아니다.

## 7. 유효성 검사

이벤트를 처리하기 전에 다음 사항을 검사한다.

1. JSON 객체인지 확인한다.
2. 필수 필드의 존재 여부를 확인한다.
3. 각 필드의 자료형을 확인한다.
4. 스키마 버전과 UUID 형식을 검증한다.
5. 시간 문자열이 올바른 UTC 형식인지 확인한다.
6. 지원되는 이벤트 유형인지 확인한다.
7. 이벤트 유형별 `attributes` 규칙을 검증한다.
8. JSON의 최상위 필드와 `attributes` 내부에 동일한 이름의 필드가 중복되면 해당 이벤트를 거부한다.

유효하지 않은 이벤트는 정상 이벤트로 처리하지 않고 오류를 반환한다.

## 8. 설계 원칙

- 로그 수집과 위협 탐지를 분리한다.
- 이벤트 자체에 공격 여부를 확정하는 판단을 포함하지 않는다.
- 원본 로그 전체를 무조건 전송하지 않는다.
- 민감정보는 수집 및 전송을 최소화한다.
- 이벤트 데이터 형식과 네트워크 통신 규격을 분리한다.
- 스키마 변경 시 버전과 호환성을 검토한다.

## 9. 향후 확장

초기 스키마 검증과 테스트를 완료한 후 다음 기능을 검토한다.

- 추가 인증 및 시스템 이벤트 유형
- 이벤트 중복 처리
- 탐지 결과를 위한 별도 데이터 구조
- 이벤트 배치 전송
- 전송 실패 시 재시도 및 복구
- 이벤트 무결성과 송신자 인증
